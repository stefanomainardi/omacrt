# What a mode change does to the signal, seen at the converter.
#
# Measured 2026-09-13 on the BeoCenter 1 chain: RX 7700/7800 XT, amdgpu,
# RGB-Pi 2 over HDMI. `omacrt dac poll` samples the converter's lock register
# over i2c every millisecond and reports only the transitions; it does not
# reset the converter, which `omacrt dac watch` would, and which would have
# repaired the thing being measured half way through it.
#
# The compositor's own timestamps come from its log, which carries the wall
# clock on every line. The two are lined up on that clock.
#
# 4224 reads over 8000 ms, none refused by the bus: the i2c side answers
# throughout, including while the display controller is being reprogrammed.
#
#   NTSC to PAL, requested at 10:47:30.866
#     +118 ms   the converter loses lock
#     +222 ms   first vblank: drmModeAtomicCommit returns
#     +400 ms   the converter has lock again
#     no lock for 282 ms
#
#   PAL to NTSC, requested at 10:47:33.893
#     +109 ms   the converter loses lock
#     +182 ms   first vblank: drmModeAtomicCommit returns
#     +388 ms   the converter has lock again
#     no lock for 279 ms
#
# Three things follow.
#
# The signal is still good for the first 110 ms of a call that blocks for 200.
# Whatever amdgpu spends that time on, it is not yet disturbing the output.
#
# The cost is larger than the 182 to 229 ms this project published, not
# smaller. That figure is how long the kernel's commit blocks. The converter
# has nothing to lock to for 280 ms.
#
# A third of that is after the driver has returned: scanout is running again
# and the converter still needs 170 to 200 ms to acquire it. That is a
# property of the RGB-Pi 2 rather than of the driver or of this project, so a
# different converter moves the total.
#
# What this does not measure is the television. A converter with no lock is
# not the same as a dark screen, and what the tube does across those 280 ms
# needs a camera pointed at the glass.

# t_ms    state            (t0 = 10:47:28.865)

# A second walk, 2026-09-13 12:13, looking for a timing change that is cheap.
# Each step held 2.5 s, read from the compositor's log as the first vblank
# after the request. Every modeline below keeps the 72 MHz clock and the
# 15.731 kHz line rate, so none of them is asking the set for anything new.
#
#   the same timing again                      already set, nothing done
#   one horizontal sync edge, +16 samples      195.0 ms
#   one vertical sync edge, +1 line            207.0 ms
#   active lines 240 to 224, vtotal unchanged  202.3 ms
#   vtotal 262 to 264                          197.9 ms
#   back to the base timing                    193.6 ms
#
# There is no cheap category. A timing is either the one already programmed,
# which the compositor now detects and does nothing about, or it is a full
# modeset at about 200 ms.

# And what the television does, filmed 2026-09-13 13:16.
#
# Six mode changes four seconds apart, between two timings that differ only in
# their vertical total, 262 and 264, so the picture before and after is the
# same and the only thing that changes on the glass is the interruption. Both
# keep the 72 MHz clock and the 15.731 kHz line rate.
#
# Filmed at 240 fps on a phone held still, the whole screen in frame. The time
# base is calibrated by the film itself and not by its metadata: the changes
# are 4.000 s apart by construction and land 961 frames apart, which is
# 240.25 fps, 4.163 ms a frame.
#
# Measured as the mean brightness of a crop containing only the screen. The
# minimum inside each interruption is 0.1 to 0.3 out of a median of 41.8, so
# the tube is black rather than showing anything disturbed.
#
#   change   dark frames   ms
#     1          93       387
#     2          97       404
#     3         136       566
#     4          94       391
#     5          96       400
#
# The sixth is not in the film. Median 400 ms.
#
# So the three numbers for one mode change, on this chain:
#
#   195 ms   the kernel's commit call blocks
#   280 ms   the converter has nothing to lock to
#   400 ms   the television shows nothing
#
# The tube adds about 120 ms of its own after the converter has reacquired,
# and the whole thing is roughly twice the figure this project published as
# the cost of a mode change. That figure was the kernel's part of it, measured
# correctly and described as though it were the whole. One of the five was
# 566 ms, 40% worse than the median, so it is not constant either.
