# Re-verifying everything before publishing it

Nothing in this project had been published outside the repository when this
was written. Before anything was, every factual claim in
[`flyback.md`](flyback.md), [`15khz.md`](15khz.md) and
[`comparison.md`](comparison.md) was checked again: kernel claims against the
source of the kernel that actually runs here, measurements by re-running the
instrument, and claims about other projects against their own documentation.

Four claims did not survive. Two of this project's own bugs were found by the
checking rather than by using the software. This is the record, kept because
a number is worth what its provenance is worth.

**Method.** The kernel is Arch's `linux 7.2.4.arch1-2`. Kernel claims are
pinned to a file and a line in the upstream tree at tag `v7.2.4`, fetched for
this audit. Measurements were re-run on the same chain the originals were
taken on: a BeoCenter 1 through an RGB-Pi 2, 3520x240 at 60.041 Hz, over a
leased HDMI connector on a Radeon RX 7700/7800 XT (Navi 32, DCN 3.2). Two
readings could not be re-taken because they need root, which is noted where
it applies.

---

## Refuted

### The cost of a mode change

**Was:** "an atomic commit that carries a new modeline blocks for 166 to
190 ms, whether it moves the whole standard or only the vertical total."

**Verdict: wrong, and unreproducible as published.** The clock meant to
measure it was declared, zeroed and read, and never assigned a value, so the
log line it feeds had never been printed in the life of the project. The
figure could not be reproduced from any log because no log ever contained it.
The field is set now, at the moment the modeline is asked for, and read at
the first vblank after it.

**Is:** re-measured, eight changes through the leased connector, time from
the request to the first vblank:

| what moved | first vblank after the request |
| --- | --- |
| nothing: the same timing re-applied | 4.4, 8.8, 9.7, 15.5 ms |
| the vertical total alone | 196.5, 196.8, 206.8, 212.2 ms |
| the whole standard, NTSC to PAL and back | 182.4, 192.9, 216.7, 226.1 ms |

So the second half of the original claim holds — it does not matter how
little of the timing moves — and the range is **182 to 229 ms**. The first
row is new and is the one that shows the cost is the modeset itself rather
than anything this compositor does.

### `amdgpu.freesync_video=1` is required for a variable refresh rate

**Was:** "two things set … 2. `amdgpu.freesync_video=1` on the kernel command
line. Without it the config computed for the CRTC is overwritten a few lines
further on and the state falls back to `VRR_STATE_INACTIVE`."

**Verdict: not supported by the source, and not observed.** The state this
project uses is `VRR_STATE_ACTIVE_VARIABLE`, and
`get_freesync_config_for_crtc` sets it from exactly two things: the connector
being `freesync_capable` with the mode's refresh inside the declared range,
and the CRTC's `vrr_enabled`, which is the atomic `VRR_ENABLED` property.[^1]
The module parameter is not on that path. What it gates is a different
mechanism: a seamless change of the front porch that skips the modeset and
produces `VRR_STATE_ACTIVE_FIXED`.[^2]

That mechanism was then tested directly, with the parameter set and a timing
shaped exactly as the driver's own condition requires — same clock, same
htotal, vertical total moved, `vsync_start` moved with it, sync width
unchanged.[^3] It still cost 222.8 and 229.1 ms. The seamless path does not
trigger on this chain.

**Is:** the parameter has not been shown to do anything here. The definitive
test is a boot without it, which is pending.

### Press to picture

**Was:** "best 7.4 ms, median 20.4 ms (1.23 frames), worst 32.1 ms. About
half a frame of that is the program's own input sampling."

**Verdict: superseded.** That reading predates the scheduling fixes made on
the day of this audit. Re-run, 300 presses of a virtual pad at random points
of the frame: **best 1.46, median 10.19 (0.61 frames), 95th 17.52, worst
18.21 ms.** Every sample is in
[`data/press-to-picture.txt`](data/press-to-picture.txt).

The explanation also changes, and the new one is better. Of the median,
**8.33 ms is half a frame** — what any commit at a random phase waits for the
next vblank, whoever is compositing. The compositor's own contribution is the
1.9 ms above that. The instrument measures its own overhead at 0.01 ms. A
real pad adds its own polling, one to eight milliseconds by its rate, which
is the pad's and not this.

### The refresh rates the tube was given

**Was:** "the tube delivers 59.922, 57.499, 55.000 and 49.999 Hz, with six to
sixty microseconds between one frame and the next."

**Verdict: not reproducible, and internally inconsistent.** No instrument in
this repository produces that precision today, and the 49.999 row contradicts
this project's own configuration: `output.vrr_min_hz` is 55 and a slower
request is held there, which the `rate` command says out loud.

**Is:** measured as the median of the last 300 vblank intervals, fifteen
seconds of settling at each step: asked 60.041 gives 60.04, asked 59.92 gives
60.02, asked 57.5 gives 57.59, asked 55 gives 55.01, and asked 50 is held at
55. The instrument is coarse — it is a median over a five second window — and
the numbers are reported to the precision it actually has.

## Found by the checking

Two defects in this project, neither of which showed up in use.

**The mode change clock was never armed.** Above. A measurement instrument
that is never started reports nothing, and nothing is indistinguishable from
a log that has rotated.

**The two explanations on `rate` were swapped.** They compare periods, not
frequencies, so a longer period is a slower rate. Asking for a rate below
`output.vrr_min_hz` answered "the mode itself is no faster than that", which
is the opposite of what had happened. Both are fixed.

## Verified

### The five things that refuse interlace

All five hold in `v7.2.4`, and each is now pinned:

1. `fill_stream_properties_from_drm_display_mode` never copies
   `DRM_MODE_FLAG_INTERLACE` into the timing.[^4] The only mention of the
   flag in the whole of `amdgpu_dm.c` is the rejection in
   `amdgpu_dm_connector_mode_valid`.[^5]
2. `optc1_validate_timing` returns false for any interlaced timing, under the
   comment *"Temporarily blocking interlacing mode until it's supported"*.[^6]
3. `OTG_INTERLACE_CONTROL` is in the DCN 1 register list and absent from DCN
   3.2's, though the code that would write it is generation-independent and
   already there.[^7] AMD's own headers for this ASIC carry the register and
   its enable bit.[^8]
4. DML1, which DCN 3.2 validates through,[^9] doubles the vertical ratio for
   an interlaced timing when the ASIC does not claim `ptoi_supported`,[^10]
   and `dcn3_2_ip` sets that false.[^11]
5. `interleave_en` exists in the line buffer parameters[^12] and is never set
   from the timing: both `dcn10_hwseq.c` and `dcn20_hwseq.c` set the other
   two fields beside it and not that one.[^13]

One clause was removed. The original said the doubled ratio "then fails the
scaler taps validation". The doubling is in the source; that it is what fails
was not traced, and is now stated as unknown.

### The variable refresh range

`MIN_REFRESH_RANGE` is 10, and it gates `VRR_STATE_ACTIVE_VARIABLE` after the
declared maximum has been capped at the mode's own nominal rate.[^14] So a
declared 55 to 66 against a 60.041 Hz mode becomes 55 to 60.041, a range of
5.04, and is refused in silence. That claim stands.

One number was made precise. The original said amdgpu "refuses one narrower
than ten hertz". There are two different checks: capability requires the
declared range to be **strictly greater than 10**,[^15] and the active state
requires the capped range to be **10 or more**.[^16] A declared range of
exactly 10 fails the first and never reaches the second.

### The vendor block nobody in the kernel parses

The nine bytes this project writes into the EDID — `68 1a 00 00 01 01 <min>
<max> 00` — were worked out by trying them, not read out of a specification.
That is now explained rather than merely admitted: **no kernel code parses
them.** The CEA block is handed to the display microcontroller and the
firmware returns a version, a minimum and a maximum.[^17] There is nothing in
the tree to read.

The last byte is the flags, and this project deliberately leaves it zero.
That turns out to be load-bearing: if the block declares an MCCS control
code, the driver then requires the display to support FreeSync over MCCS and
**revokes** the capability when it does not.[^18] A television does not. The
empirical choice was right for a reason nobody had looked up.

### The measurements that stand

Re-run on the day of the audit, launcher mapped underneath:

| | |
| --- | --- |
| commit to start of scanout, variable rate, client drawing 1 / 2 / 4 ms | 3.79 / 4.61 / 6.54 ms |
| the same at a fixed rate | 6.98 / 7.90 / 9.79 ms |
| the launcher end to end, `omacrt status` | 2.0 ms |

**The starting point is now reproducible instead of remembered.** The
published "30.9 ms before any of this work" was a number from history. Turn
the three switches off — `FLYBACK_LATE_DRAW=off`, `FLYBACK_MARGIN_US=off`,
and the variable rate off, which together are what every other compositor
does — and the same client measures **33.36 ms, two frames exactly**, with
the launcher's own figure at 33.1 ms. That is the honest comparison, and
anybody can run it.

The height and brightness table is unchanged. It was measured from film of
the set, each step held for eight seconds, height taken against the picture's
own width so the camera's drift cancels. It cannot be re-derived without the
recordings, and the method is stated wherever the table appears.

### What could not be re-checked

Two readings need root, which this session does not have. Both are reported
with the date they were taken and neither is load-bearing on its own.

- `amdgpu_dm_dtn_log` reporting `vmin 261 vmax 327` for the tube's timing
  generator. It is at least internally consistent: those registers hold the
  total minus one,[^19] so 261 is the 262 line mode and 327 is 328 lines,
  which at 15730.8 Hz is 47.96 Hz — the 48 Hz declared in the EDID.
- The driver logging `VRR packet update: enabled=1 state=3`. `dmesg` is
  restricted on this machine.
